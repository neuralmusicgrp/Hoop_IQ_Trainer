# v0.9.2 Supabase Schema Planning

## 1. Purpose

This planning release describes the future Supabase database schema needed for Hoop IQ Trainer coach, player, and team features. It expands the v0.9.1 Supabase provider decision into a table-level plan while keeping the current public/offline app unchanged.

This is documentation only. It does not create tables, add SQL, connect to Supabase, add live Supabase integration, or introduce live authentication.

## 2. Release Type

Planning / Schema Design Record

## 3. Version

v0.9.2-supabase-schema-planning

## 4. Planned Tables

### profiles

Purpose:
Stores one application profile for each authenticated user. This is the app-facing identity layer for coaches and players, separate from Supabase Auth internals.

Key fields:
- id
- auth_user_id
- display_name
- role
- email
- created_at
- updated_at

Connections:
- One profile can own many teams as a coach.
- One profile can belong to many teams through team_members.
- One profile can receive many player_progress records.
- One profile can create assignments, coach_term_overrides, invite_codes, and audit_events.

### teams

Purpose:
Stores coach-created teams or groups, such as a school team, club team, training group, or classroom-style basketball IQ cohort.

Key fields:
- id
- name
- owner_profile_id
- season_label
- status
- created_at
- updated_at

Connections:
- Each team belongs to one coach profile through owner_profile_id.
- Each team has many team_members.
- Each team can have many invite_codes.
- Each team can have many assignments.
- Each team can have many player_progress records through assignment and membership context.
- Each team can have many coach_term_overrides.

### team_members

Purpose:
Connects profiles to teams and records the role of each person inside that team.

Key fields:
- id
- team_id
- profile_id
- member_role
- status
- joined_at
- invited_by_profile_id

Connections:
- Joins profiles to teams.
- Allows a profile to be a coach on one team and a player on another if the product later allows that.
- Supports RLS checks for whether a player belongs to a team or whether a coach can manage team data.
- Connects invite_codes to the accepted membership path.

### invite_codes

Purpose:
Stores coach-created join codes that allow players to request or create membership in a team without public player search.

Key fields:
- id
- team_id
- code_hash
- created_by_profile_id
- status
- expires_at
- max_uses
- use_count
- created_at

Connections:
- Each invite code belongs to one team.
- Each invite code is created by one coach profile.
- Accepted invite codes lead to team_members records.
- audit_events can record invite code creation, use, expiration, and revocation.

### assignments

Purpose:
Stores coach-created practice assignments, quizzes, or study sets for a team.

Key fields:
- id
- team_id
- created_by_profile_id
- title
- instructions
- due_at
- status
- created_at
- updated_at

Connections:
- Each assignment belongs to one team.
- Each assignment is created by one coach profile.
- Each assignment has many assignment_terms.
- Each assignment can have many player_progress records.

### assignment_terms

Purpose:
Stores the selected Hoop IQ Trainer terms/actions included in an assignment and their intended order or emphasis.

Key fields:
- id
- assignment_id
- term_id
- sort_order
- required
- created_at

Connections:
- Each assignment_term belongs to one assignment.
- term_id references the app's stable basketball term identifier, not a new editable definition.
- player_progress can connect back to assignment_terms when tracking completion by term/action.

### player_progress

Purpose:
Stores player activity and completion results for future synced progress, team dashboards, and coach review.

Key fields:
- id
- team_id
- assignment_id
- assignment_term_id
- player_profile_id
- activity_type
- score
- attempts
- completed
- completed_at
- last_activity_at
- created_at
- updated_at

Connections:
- Each progress row belongs to one player profile.
- Each progress row belongs to one team.
- Progress may connect to an assignment and assignment_term when the work is assigned.
- Coaches can view progress only for players on teams they own or coach.
- Players can view their own progress.

### coach_term_overrides

Purpose:
Stores future coach-specific notes or teaching emphasis for existing terms without changing the global app term definitions.

Key fields:
- id
- team_id
- term_id
- coach_profile_id
- custom_note
- emphasis
- status
- created_at
- updated_at

Connections:
- Each override belongs to one team.
- Each override is created by one coach profile.
- term_id references the stable app term identifier.
- Overrides can be shown only inside that team context.

### audit_events

Purpose:
Stores important account, team, invite, assignment, and progress events for troubleshooting, privacy review, and coach accountability.

Key fields:
- id
- actor_profile_id
- team_id
- event_type
- target_table
- target_id
- summary
- created_at

Connections:
- Events can optionally connect to the acting profile.
- Events can optionally connect to a team.
- Events can reference invite_codes, assignments, team_members, player_progress, or coach_term_overrides through target_table and target_id.
- Audit rows support later moderation and support workflows without exposing private data broadly.

## 5. Relationship Map

- profiles own teams through teams.owner_profile_id.
- profiles join teams through team_members.profile_id.
- teams contain team_members, invite_codes, assignments, coach_term_overrides, and player_progress.
- invite_codes belong to teams and are created by coach profiles; successful use creates team_members rows.
- assignments belong to teams and are created by coach profiles.
- assignment_terms belong to assignments and point to stable app term ids.
- player_progress belongs to a player profile, a team, and optionally an assignment or assignment_term.
- coach_term_overrides belong to teams, coach profiles, and stable app term ids.
- audit_events can reference the actor profile, team, and target record involved in an important action.

## 6. Planned Indexes

Planning indexes only:

- profiles.auth_user_id for looking up the app profile from the authenticated user.
- teams.owner_profile_id for coach dashboard team lists.
- team_members.team_id and team_members.profile_id for membership checks.
- team_members.team_id plus profile_id for duplicate-membership prevention and RLS joins.
- invite_codes.team_id for team-level invite management.
- invite_codes.code_hash for invite-code validation.
- assignments.team_id for team assignment lists.
- assignment_terms.assignment_id for loading assignment contents.
- assignment_terms.assignment_id plus term_id for preventing duplicate terms in one assignment.
- player_progress.player_profile_id for player history.
- player_progress.team_id plus assignment_id for coach dashboard summaries.
- player_progress.assignment_term_id for term-level completion tracking.
- coach_term_overrides.team_id plus term_id for team-specific term note lookup.
- audit_events.team_id plus created_at for team audit review.
- audit_events.actor_profile_id plus created_at for account activity review.

## 7. Planned Constraints

Planning constraints only:

- profiles.auth_user_id should be unique.
- teams.owner_profile_id should require an existing coach profile.
- team_members should require valid team_id and profile_id values.
- team_members should prevent duplicate active membership for the same team and profile.
- team_members.member_role should be limited to planned app roles such as coach, player, and assistant when those roles are finalized.
- invite_codes.code_hash should be unique while active.
- invite_codes.use_count should not exceed max_uses when max_uses is set.
- assignments.team_id and created_by_profile_id should reference existing records.
- assignment_terms.assignment_id should reference an existing assignment.
- assignment_terms.term_id should match a stable app term id.
- player_progress.player_profile_id should reference an existing profile.
- player_progress.score and attempts should use non-negative values.
- coach_term_overrides should not modify global term definitions.
- audit_events should preserve enough actor, target, and timestamp context to support review.

## 8. Plain-Language RLS and Privacy Notes

- Enable RLS on every future app table that is exposed through Supabase.
- Guests should not read or write private team, roster, assignment, invite, or progress data.
- A user should read and update only their own profile unless a later admin role is deliberately added.
- Coaches should manage only teams they own or are assigned to coach through team_members.
- Players should see only teams they belong to.
- Coaches should see player_progress only for players on their own teams.
- Players should see only their own player_progress.
- Invite-code validation should not expose rosters, player names, or full team records before membership is accepted.
- RLS policies should combine authenticated access with ownership or membership checks; authenticated status alone is not enough.
- Update policies should preserve ownership and membership boundaries after edits.
- Do not use user-editable profile metadata as the source of authorization decisions.
- Youth/player data should be treated as private by default, with public sharing avoided unless a future policy explicitly approves it.
