# v0.9.1 Supabase Auth Provider Selection

## 1. Purpose

This planning release selects Supabase as the planned auth/backend provider for future Hoop IQ Trainer coach, player, and team features. It records the direction before any implementation work begins so the current public/offline app stays stable while the authenticated team version is designed deliberately.

## 2. Release Type

Planning / Architecture Decision Record

## 3. Version

v0.9.1-supabase-auth-provider-selection

## 4. Decision

Provider selected: Supabase

## 5. Why Supabase

- Supabase Auth can support future coach/player sign-in, including email/password or magic-link style flows.
- Supabase Postgres fits relational team data such as users, teams, team_members, invite_codes, assignments, and player_progress.
- Row Level Security is important for protecting youth, player, and team data with row-level access rules.
- Supabase can support future synced player progress, coach dashboards, team rosters, and assignment views.
- Supabase avoids building custom authentication from scratch, which reduces security risk and implementation burden.

## 6. Planned Future Supabase Tables

Planning table names only:

- profiles
- teams
- team_members
- invite_codes
- assignments
- assignment_terms
- player_progress
- coach_term_overrides
- audit_events

## 7. Planned Authentication Approach

The early authenticated beta should start with:

- Email/password or magic link.
- No public player search.
- No social login required for early beta.
- No player-to-player messaging.
- Coach-created team invite codes later.
- Guardian/parent policy to be reviewed before youth launch.

## 8. Planned RLS Rules

Plain-language Row Level Security planning rules:

- Users can read and update their own profile.
- Coaches can read teams they own.
- Players can read teams they belong to.
- Coaches can read progress only for players on their own teams.
- Players can read their own progress.
- Guests cannot access private team data.
- Invite codes should be validated without exposing full rosters.

Later SQL policies should use explicit authenticated-role policies plus ownership/team-membership predicates rather than broad authenticated access.

## 9. What This Release Does Not Add

This release does not add:

- Supabase project connection.
- API keys.
- Auth UI.
- SDK import.
- Backend code.
- Migrations.
- Live database.
- RLS SQL.
- Synced player progress.
